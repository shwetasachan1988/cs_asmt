# Final engineering summary

## 1. Outcome

A runnable prototype (`docker compose up -d --build`, dashboard on `http://localhost:8080/`) containing:

1. a production-style **URL shortener** (Spring Boot 3.5, Java 21, PostgreSQL, Redis), and
2. an **agentic SDLC orchestrator** that turns a requirement into reviewable engineering output - requirements, design, code, tests,
   documentation, release readiness - with a stateful DAG engine, entry/exit gates, parallel branches with joins, human approval
   checkpoints, bounded retries, fallback, rollback, safe-stop, policy guardrails, hash-chained audit, decision lineage, reliability
   metrics and dynamic re-planning.

Three scenarios (greenfield, brownfield, ambiguous) run end to end on the real stack; 68 automated tests pass; four recorded runs are
committed under `docs/runs/`.

## 2. Plan and rationale

The brief's differentiator is the orchestration layer, so the work was sequenced to protect it:

| Step | What | Why this order |
|---|---|---|
| 1 | Shortener first (API, cache, rate limit, analytics, tests, Docker) | the orchestrator needs a real, changing codebase to reason about; it also makes the brownfield scenario honest |
| 2 | Engine core: model, state, gates, retries/fallback/rollback, approvals, safe-stop | the hardest-to-retrofit part; designed around one invariant - *only the engine changes state* |
| 3 | Policies + audit chain + metrics | governance must exist before agents do, so agents are born constrained |
| 4 | Agents that do **real** work (scan code, compile and run generated code, execute SQL, call the live API) | evidence beats assertions; deterministic so runs and tests are reproducible |
| 5 | Scenarios, REST API, dashboard, demo driver | make the behaviour visible and reviewable |
| 6 | Run everything, read the evidence critically, fix, document | six defects found this way (see Testing doc) |

Key judgement calls (full table in [ARCHITECTURE](ARCHITECTURE.md) section 9): agents *propose*, the engine *disposes*; policies are code;
re-execute only what genuinely changed; approvals are revoked when what was approved changes; release is a dry run.

## 4. Risks, trade-offs and validation - headline

* Highest risks: agents emitting unsafe output, agents escalating scope, rubber-stamp approvals, side effects after partial failure,
  schema changes. Each has an engine-level control and a test ([risk register](TESTING_AND_RISKS.md#2-risk-register)).
* Validation is by execution: generated Java is compiled and its checks run, migrations and rollbacks run on PostgreSQL in a scratch
  schema, regressions hit the live API, the contract is parsed and its references resolved, the audit chain is verifiable.
* Verified outside the test suite: restart mid-run, Redis outage, dashboard rendering.

## 5. Assumptions

Single trusted environment; reviewers are humans using the dashboard/CLI; PostgreSQL 16 + Redis 7 available; requirements are
English text; scenarios are catalogued (new ones implement `ScenarioDefinition`).

## 6. Limitations

Agents are deterministic and rule-based (no LLM calls); approver identity is asserted, not authenticated; single-node scheduler;
generated code runs in-process behind an API allow-list (not a sandbox); migration validation does not measure locking on large
tables; no load test; Windows `mvnw.cmd` untested here. Details and mitigations in the testing document.

## 7. How AI assistance was used - and how it was kept honest

The system was built with Claude Code in a long, iterative session. The division of labour I would defend:

* **AI produced** first drafts of almost all code, tests, templates and documents.
* **Verification was not delegated.** Every behaviour claimed in these docs is backed by a failing-then-passing test or a recorded run.
  The first end-to-end run failed on its first task; the *system's own audit trail* identified the defect, which is the point of building
  audit-grade observability first. Later, reading the recorded evidence exposed a non-determinism bug that tests had not caught.
* **Human judgement stays where the brief puts it:** scope (what is real vs simulated), the autonomy boundary (what an agent may
  never do), what counts as high risk, and the decision to be explicit about limitations rather than hide them.
* The prototype embodies the same rule it enforces: *AI output is accepted only through gates that can say no.*

## 8. What I would do next

1. LLM-backed agents behind the existing contract, with the unsafe-code execution moved into an isolated container.
2. Real authentication/authorisation for approvers (OIDC), role-based approval rules per risk level.
3. Lease-based multi-instance scheduler (row locks), SSE instead of polling, external anchoring of audit hashes.
4. Testcontainers profile in CI, load test for the redirect path and the 500 ms bulk target, circuit breaker around Redis.
5. Policy-as-data (OPA/Rego) so security can change rules without a deploy.

## 9. Reviewing this in fifteen minutes

1. `docker compose up -d --build`, open `http://localhost:8080/`.
2. Start **Ambiguous** -> open node `clarify` -> answer `identified_users` for tracking -> approve. Watch the plan grow, the policy blocks
   (`impl-safety`, `impl-privacy`), the fallback, then approve design and the release.
3. Open the finished run's **Audit timeline** -> *Verify hash chain*; **Decision lineage**; **Final summary**.
4. Click `clarify` -> *Change an answer later* -> `aggregate_only` and watch dependants invalidate and approvals get revoked.
5. Start **Greenfield** with *Permanent failure* to see retries exhausted and rollback; **Brownfield** to see the plan grow from the code scan.
6. Read `engine/WorkflowEngine.java` (`advance`, `tryLaunch`, `onResult`, `handleFailure`, `failRun`) and `engine/PlanMutator.java`.
